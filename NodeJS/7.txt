# Authorization vs Authentication

## Authentication
- The process of verifying the identity of a user or system.
- Answers the question: "Who are you?"
- Example: Logging in with a username and password.

## Authorization
- The process of determining what an authenticated user is allowed to do.
- Answers the question: "What are you allowed to do?"
- Example: Checking if a logged-in user has permission to access an admin page.

## Key Differences
- Authentication comes before authorization.
- Authentication = identity verification.
- Authorization = permission validation.

## WebSocket
- A protocol enabling bidirectional communication between client and server over a single TCP connection.
- Allows real-time data exchange without repeated HTTP requests.
- Answers the need: "How do we communicate in real-time?"
- Example: Live chat applications, notifications, live updates.

## Socket.IO
- A JavaScript library that makes WebSocket implementation easier.
- Provides fallback mechanisms if WebSocket is not supported.
- Enables event-driven, real-time communication.
- Works seamlessly with Node.js and client-side JavaScript.

## Key Features
- Automatic reconnection handling.
- Broadcasting messages to multiple clients.
- Room and namespace management.
- Real-time messaging and notifications.

- **Upgrade**: `websocket` (new header specifying protocol upgrade)
- **Sec-WebSocket-Key**: Random base64-encoded value for security
- **Sec-WebSocket-Version**: `13` (WebSocket protocol version)

## Polling is a synchronous communication pattern where a client repeatedly checks (polls) a resource, service, or data source at regular intervals to see if new data is available or if a status has changed.

## Key Characteristics:
- **Repetitive Checking**: The client continuously queries the server/resource at fixed or variable intervals
- **Synchronous**: The client waits or actively checks for responses
- **Simple Implementation**: Easy to understand and implement
- **Resource Intensive**: Can consume more bandwidth and server resources since checks happen regardless of whether data exists
- **Latency**: There's a delay between when data becomes available and when the client detects it

## Common Use Cases:
- Monitoring job completion status
- Checking for new messages in a queue
- Fetching real-time data updates
- Tracking background process progress

## Alternatives:
- **Push/Webhooks**: Server pushes data to client when available
- **WebSockets**: Establishes persistent bidirectional connection
- **Event Listeners**: Client subscribes to events and gets notified automatically

## Trade-offs:
| Aspect | Polling | Event-Driven |
|--------|---------|--------------|
| Complexity | Low | Medium-High |
| Resource Usage | Higher | Lower |
| Latency | Variable | Immediate |
| Implementation | Simple | More complex |

## Polling vs WebSocket

| Feature | Polling | WebSocket |
|---------|---------|-----------|
| **Connection** | Multiple HTTP requests | Single persistent connection |
| **Communication** | Client initiates (one-way) | Bidirectional (client & server) |
| **Latency** | High (depends on interval) | Low (real-time) |
| **Resource Usage** | Higher (repeated requests) | Lower (single connection) |
| **Scalability** | Limited | Better for many clients |
| **Use Case** | Status checks, periodic updates | Live chat, notifications, real-time data |
| **Server Load** | Higher | Lower |
| **Setup Complexity** | Simple | Moderate |

### When to Use Polling:
- Simple status checks
- Non-critical updates
- Limited concurrent users
- Legacy browser support needed

### When to Use WebSocket:
- Real-time applications
- High-frequency updates
- Chat and notifications
- Live data streaming
- Modern browsers

**Node.js Streams** are objects that let you read data from a source or write data to a destination in chunks, rather than loading an entire file into memory at once.

**Why streams are essential when you have `fs.readFile`:**

1. **Memory Efficiency** - `fs.readFile` loads the entire file into RAM before you can use it. Streams process data in chunks, keeping memory usage constant regardless of file size.

2. **Performance** - You can start processing data immediately as it arrives, rather than waiting for the entire file to load.

3. **Large Files** - For gigabyte-sized files, `fs.readFile` would cause out-of-memory errors, while streams handle them gracefully.

4. **Real-time Processing** - Streams allow you to transform, filter, or pipe data as it flows through your application.

5. **Backpressure Handling** - Streams automatically manage the flow of data, preventing your application from being overwhelmed.

# HTTP Headers with Streams

## Content-Length Change
- **Without Streams**: `Content-Length: 1048576` (entire file size known upfront)
- **With Streams**: `Content-Length` may be absent or use `Transfer-Encoding: chunked`

## Transfer-Encoding Header
- **Added**: `Transfer-Encoding: chunked`
- Indicates data is sent in chunks rather than all at once
- Allows server to send data without knowing total size beforehand

## Key Differences:
| Aspect | Without Streams | With Streams |
|--------|-----------------|--------------|
| Content-Length | Present | Often absent |
| Transfer-Encoding | Not used | `chunked` |
| Memory Usage | High | Low |
| Start Time | Delayed | Immediate |
| Connection | Buffered | Continuous flow |
